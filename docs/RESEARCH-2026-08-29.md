# Marketing-site evidence checkpoint — 2026-08-29

This file records dated external evidence and rationale. It is **not Product or design authority merely by existing**. Canonical repository contracts are `VISITOR-JOURNEY.md`, `HOMEPAGE.md`, `DESIGN.md`, `MOTION.md`, `ARCHITECTURE.md`, and `VERIFICATION.md`.

## Evidence classes

Use these labels when applying this file:

- **A — controlled / peer-reviewed HCI evidence**: stronger evidence about a bounded human-computer interaction effect, not automatically a marketing conversion law.
- **B — established UX/accessibility evidence**: durable practitioner/research synthesis such as NN/g or W3C; still context-dependent.
- **C — current industry observation**: what high-quality current products do; useful pattern evidence but not causal proof.
- **D — Lunowa-specific inference**: our synthesis from Product semantics + A/B/C evidence; must be tested with actual visitors.

Do not convert C into `proven best practice`, and do not convert D into market validation.

## 1. First impression, prototypicality, and trust

### A — webpage prototypicality / trust, 2023

A 2023 International Journal of Human-Computer Studies paper studied 1,530 participants and more than 3,000 webpages. Webpage prototypicality strongly affected perceived trustworthiness and correlated with aesthetics and perceived pre-use usability. Prototypicality, aesthetics, and usability together explained 29%-68% of variance in trustworthiness depending on webpage category.

Source:
- https://www.sciencedirect.com/science/article/pii/S107158192300112X

Bounded implication:

Visitors benefit when a page is recognizable as the kind of page/Product they expect. This does **not** mean copying competitors or eliminating brand distinctiveness.

Lunowa inference:

Use familiar marketing/email-Product structure to reduce orientation cost. Put distinctiveness into Product behavior, copy, visual craft, and timing rather than making the visitor decode an unfamiliar abstract visual system.

### A — first-impression visual complexity / prototypicality

Earlier controlled research by Tuch et al. found that visual complexity and prototypicality affect aesthetic impressions at extremely short exposures, including tens of milliseconds. Lower visual complexity and higher prototypicality generally performed better in the tested conditions.

Source:
- https://www.sciencedirect.com/science/article/pii/S1071581912001127

Bounded implication:

The first screen should not require simultaneous interpretation of many visual devices. This is not a universal mandate for minimalism.

## 2. Recognition, scanning, and attention

### B — recognition over recall

NN/g's current explanation of the recognition-vs-recall heuristic states that recognizing visible choices/context is easier than retrieving information from memory because the interface supplies retrieval cues.

Source:
- https://www.nngroup.com/articles/recognition-and-recall/

Lunowa inference:

A concrete email request/reply/attachment is easier for a first-time visitor to recognize than an abstract `Managed -> Needs You -> Moment` diagram that requires learning Lunowa's vocabulary first.

### B — heading-based Layer Cake scanning

NN/g eyetracking research describes the Layer Cake pattern: users efficiently scan visually distinct, descriptive headings and selectively read the body content relevant to their task.

Sources:
- https://www.nngroup.com/articles/layer-cake-pattern-scanning/
- https://www.nngroup.com/articles/text-scanning-patterns-eyetracking/

Lunowa inference:

Major headings should carry the full narrative. The page should remain understandable if body copy is largely skipped.

### B — above-the-fold attention and scrolling

NN/g research notes that users do scroll substantially, but the content above the fold still receives disproportionate attention.

Source:
- https://www.nngroup.com/articles/scrolling-and-attention/

Lunowa inference:

The first viewport must establish category + value + a real Product cue. Lower sections may be long if they are clearly chunked and answer distinct visitor questions.

## 3. Motion evidence

### A — 2026 microinteraction animation experiment

A July 2026 Displays paper compared passive spinner, passive cartoon, and interactive cartoon animations in controlled 10-second waiting scenarios with 705 participants. Animation type produced different emotional and time-perception effects; interactive cartoon animation had favorable results in that bounded context.

Source:
- https://www.sciencedirect.com/science/article/pii/S0141938226000995

Boundary:

This is evidence that animation design can affect UX in waiting/microinteraction contexts. It is **not** proof that animated SaaS Heroes universally improve comprehension or conversion.

Lunowa inference:

Use motion only where Lunowa's temporal mechanism is itself the information: an intermediate reply arrives, but user attention is still unnecessary; later material evidence changes that state. Static vs motion Hero should be tested.

### B — reduced motion / accessibility

W3C WCAG 2.2 Technique C39 documents `prefers-reduced-motion` as a way to suppress non-essential motion for users who request it.

Sources:
- https://www.w3.org/WAI/WCAG22/Techniques/css/C39.html
- https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html

Implication:

Reduced-motion behavior is an acceptance path, not optional polish. Basic Product comprehension must survive without animation.

## 4. Current high-end Product-marketing observations

These are **C-class observations**, not causal evidence.

### Linear — real Product UI + calmer hierarchy

Linear's current homepage makes the Product category explicit and places realistic Linear UI near the top of the page. Its March 2026 UI refresh describes a calmer, more consistent interface designed to improve scanning, orientation, and focus; supporting navigation recedes while task-relevant content stands out.

Sources:
- https://linear.app/
- https://linear.app/now/behind-the-latest-design-refresh
- https://linear.app/changelog/2026-03-12-ui-refresh

Lunowa inference:

The Product itself should be a major visual proof, and supporting chrome should not compete for attention.

### Granola — narrow category + concrete Product surfaces + temporal usage story

Granola currently opens with a narrow category statement (`AI notepad for back-to-back meetings`) and realistic notes UI. Lower sections explain the Product around before/during/after meeting use and concrete workflow consequences.

Source:
- https://www.granola.ai/

Lunowa inference:

A recognizable concrete Product surface plus one coherent temporal scenario can teach a new category better than disconnected feature cards.

### Cursor — explicit category + interactive Product demo

Cursor's current homepage explicitly describes itself as a coding agent and includes an interactive demo showing multiple real-looking Cursor interfaces.

Source:
- https://cursor.com/

Lunowa inference:

Interactive Product proof is a viable high-end pattern when the interface itself communicates what the Product does.

### Attio — Product UI as proof across the page

Attio currently establishes its category/promise and repeatedly uses realistic CRM/agent/workflow Product surfaces to explain value.

Source:
- https://attio.com/

### Fyxer / Shortwave — category clarity and competitive overlap

Fyxer currently leads with inbox organization and reply drafting and immediately shows a recognizable inbox. Shortwave explicitly leads with AI email automation and then explains organizing, writing, search, filtering, follow-up, and related email capabilities.

Sources:
- https://www.fyxer.com/
- https://www.shortwave.com/

Lunowa inference:

If Lunowa leads with `AI email assistant`, visitors are likely to place it in an already crowded category. The homepage must show the unresolved-outcome monitoring behavior rather than merely claim `AI` differentiation.

## 5. OpenAI current frontend-generation guidance

### C / tool-generation evidence — OpenAI, 2026

OpenAI's current `Designing delightful frontends with GPT-5.4` guidance explicitly notes that underspecified prompts tend to fall back to high-frequency training patterns, producing plausible but generic layouts and weaker visual hierarchy.

The guide recommends:

- define visual constraints/design system upfront;
- generate/provide visual references before implementation;
- ground the design in real content;
- treat the first viewport as one composition;
- use one dominant visual anchor;
- default away from generic cards/hero cards/pill clusters/stat strips/icon rows;
- use imagery that shows the real product/place/context rather than decorative gradients as the primary idea;
- avoid purple/dark-mode bias;
- structure the page as a narrative;
- make each section do one job;
- verify desktop/mobile behavior.

Source:
- https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4

Important boundary:

This is guidance for steering generated frontends, not an independent HCI trial. It is directly relevant to avoiding generative-model default aesthetics, including the failure seen in Lunowa's first dark/purple/orb visual candidate.

## 6. Rejected initial generated visual — evidence from our own process

The first generated M10-style visual candidate is not accepted as visual authority.

Observed failure classes:

- generic dark navy / purple / glow / planet-orb visual prior;
- primary visual became an abstract icon/timeline explanation rather than recognizable Product use;
- weak first-glance category comprehension;
- contradiction with existing visual anti-patterns;
- generated unsupported marketing/security claims;
- excessive reliance on prior knowledge of Lunowa's internal state names.

This is a **single local design failure**, not experimental proof that dark themes, timelines, or animation are universally inferior.

Preserve only the useful semantic storyboard:

`request -> monitoring -> intermediate reply -> still no user action -> material outcome -> attention required -> context/source`.

## 7. AI-native frontend workflow

### OpenAI: visual direction -> Codex -> browser

OpenAI's current Codex/front-end guidance supports a concept-first workflow:

- research/real content first;
- generate or collect multiple visual references;
- select a direction;
- let Codex implement scoped tasks;
- open the real app/site in a browser;
- verify and iterate from actual rendered output rather than code inspection alone.

Sources:
- https://learn.chatgpt.com/codex/use-cases/idea-to-proof-of-concept
- https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4

Implication:

`research -> visitor contract -> visual variants -> comprehension evidence -> selected oracle -> Codex implementation -> browser verification` is preferable to one-shot prompt-to-site generation.

## 8. Static-first architecture

### Astro Islands

Astro's documentation states that UI components render to HTML/CSS by default with client-side JavaScript removed unless a `client:*` directive explicitly hydrates an interactive island. `client:visible` can defer hydration until a component enters the viewport.

Source:
- https://docs.astro.build/ja/concepts/islands/

Implication:

For a marketing site whose body is mostly static content but whose Product demo needs React/Motion, Astro Islands provide a strong fit: static-by-default with targeted JavaScript.

## 11. Current synthesis

Current strongest D-class Lunowa-specific synthesis:

```text
Product truth
-> visitor-question contract
-> concrete real-email scenario
-> materially different Hero concepts
-> directional 10-second comprehension test
-> select visual oracle
-> static-first implementation
-> targeted React/Motion temporal proof
-> real-browser comparison
-> visual + ARIA + interaction regression
-> accessibility/performance/security audit
-> independent full acceptance audit
```

The decisive design criterion is **correct visitor mental model**, not maximal animation or similarity to any single admired SaaS homepage.

This evidence checkpoint should be refreshed before major architecture/tooling/design-policy changes; it does not freeze vendor versions or claim a scientifically unique optimal homepage.
